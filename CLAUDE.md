# ЭТрН-бот — инструкция для агента

Телеграм-бот для бухгалтерии. Принимает пачку разрозненных документов по рейсу
и собирает два документа:

- **заявку перевозчику** — DOCX на подпись плюс текст для мессенджера;
- **транспортную накладную, Титул 1** — XML под загрузку в Saby (СБИС).

С 01.09.2026 ЭТрН обязательна, объём — до 10 рейсов в день.

Читай этот файл целиком перед первой правкой. Правила ниже не обсуждаются:
они выведены из юридической природы документа, а не из вкуса.

---

## 1. Незыблемые правила

1. **Бот не подписывает и не отправляет.** УКЭП остаётся у человека.
   Результат работы бота — черновик, готовый к подписи. Любая задача,
   формулировка которой предполагает автоотправку, — ошибка постановки:
   остановись и спроси.
2. **XML собирает шаблон, не языковая модель.** Модель извлекает значения
   из сканов и на этом её роль заканчивается. Генерация разметки моделью
   запрещена.
3. **Ни один файл не уходит человеку без валидации по XSD.** Не прошло схему —
   это наш баг, а не проблема бухгалтерии. `build_title1` обязан возвращать
   ошибки, а не «почти валидный» файл.
4. **Поля `never_guess` не заполняются автоматически.** Никогда. Ни умолчанием,
   ни эвристикой, ни «самым вероятным значением». Только человек или документ.
   Список: ИНН всех сторон, наименование и масса груза, количество мест,
   адреса погрузки и выгрузки, дата подачи ТС, госномер, ФИО водителя, ВУ.
5. **Каждое значение показывается человеку с источником** перед сборкой XML.
   Молча подставленное значение — это ошибка, которую никто не заметит.
6. **Исходники документов удаляются сразу после извлечения.** Фото ВУ и
   паспортов не хранятся ни на диске, ни в логах, ни в истории сообщений бота.
7. **Порог уверенности 0.75.** Ниже — бот обязан переспросить, а не принять.
8. **Рутину не спрашиваем по одному.** Поля с `routine=True` — коммерческая
   политика организации, а не свойства рейса. Они показываются блоком в карточке
   и правятся кнопкой. Превращать их в отдельные вопросы запрещено: восемь
   подряд «подтвердите» — это не помощь.

## 3. Карта заполнения поля

Порядок стратегий: **человек → документ → справочник → вычисление → умолчание.**
Спрашиваем только то, что не добыли сами.

```
EXTRACT  распознать из присланных документов
LOOKUP   справочник по ИНН / госномеру / номеру ВУ
DERIVE   вычислить (номер, дата, плановая дата выгрузки)
DEFAULT  политика организации
ASK      спросить человека
DEFER    чужое поле: перевозчик, получатель или ГИС ЭПД
```

Обработка «не знаю» (`Resolver.dont_know`) — пять исходов в этом порядке:
чужое поле → пропуск с объяснением; повторный поиск в справочнике; умолчание
с показом значения; необязательное → пусто; `never_guess` → отказ угадывать
плюс подсказка, где взять.

## 4. Очередь задач

Строго по порядку. Каждая задача закрывается критерием приёмки, а не ощущением.

### Задача 1. XSD и сверка реестра — СДЕЛАНО 09.09.2026

Схемы скачаны с сайта ФНС (приложение № 1 к приказу ЕД-7-26/1065@, формат 5.01,
часть 973 — восемь титулов). Уточнение: редакция «от 24.07.2026» относится к
тексту приказа; свежие XSD на сайте — от 31.10.2025 и только для титула 7,
титул 1 — от 05.02.2025. Разбор формата — `docs/ФОРМАТ_Титул1.md`.

`check_registry` печатает обе дельты пустыми: 78 полей реестра против 82
обязательных узлов схемы, 974 узла всего.

- Написать `etrn_bot/tools/check_registry.py`: сопоставляет `REGISTRY` со схемой
  и печатает две дельты — поля реестра без соответствия в схеме и обязательные
  элементы схемы, не покрытые реестром.
- Проставить в реестре `xsd=` и снять `verify=True` у сверенных полей.
- Расхождения не «чинить молча»: если схема требует поле, которого нет в реестре,
  добавить его со стратегиями и вопросом, а не заглушкой.

**Приёмка:** `check_registry` печатает обе дельты пустыми.

### Задача 2. Шаблон XML — СДЕЛАНО 09.09.2026

Шаблон собран, `filename()` реализован по разделу II приказа
(`ON_TRNACLGROT_A_E_O_W_ГГГГММДД_N.xml`). Три фикстуры дают файлы, проходящие
валидацию без ошибок. **Оговорка:** `A`, `E`, `O` — идентификаторы участников
ЭДО, их присваивает оператор; без них `filename()` осознанно отказывается
работать, а не подставляет заглушку.

Что было в задаче:

- `templates/title1.xml.j2` по сверенному маппингу.
- Реализовать `filename()` по шаблону имени файла обмена из приказа
  (включает GUID; отклонение = автоматический отказ у оператора).

**Приёмка:** `build_title1` на трёх фикстурах даёт файлы, проходящие
`schema.validate` без ошибок.

### Задача 4. Распознавание — СДЕЛАНО 09.09.2026 (на печатном документе)

Проверялись три способа на печатной заявке. Языковая модель на процессоре
Hermes: 653 с и **ноль** полей. OCR (`tesseract -l rus+eng`) плюс разбор по
подписям: **0.4 с и 23 поля**, на пустом листе — ноль. Модель с сервера удалена,
замеры и обоснование — `docs/распознавание.md`.

Итоговая схема: OCR даёт текст → `textscan` достаёт реквизиты по подписям →
парсеры проверяют (ИНН по контрольной сумме, госномер по формату) → значения
идут человеку с уверенностью не выше 0.85 и ссылкой на строку документа.

`vlm.py` остаётся для случаев, где OCR слаб (фото ВУ, рукописные правки):
OpenAI-совместимый клиент, ретраи на невалидный JSON, режим `json` для сильной
модели. **Не проверено:** фото настоящего ВУ — нужен реальный пример.

Что было в задаче:

- Промпт не писать руками — он строится из реестра (`build_schema_prompt`).
- Ретраи на невалидный JSON, максимум два, потом честный отказ.
- Вызов модели — блокирующий: в хендлерах оборачивать в `asyncio.to_thread`.

**Приёмка:** на фото ВУ и скане заявки возвращает JSON по схеме; на пустом
листе возвращает `{}`, а не выдумку.

### Задача 5. Довести `bot.py` до запуска — СДЕЛАНО 09.09.2026 (кроме живого прогона)

Все пять дефектов устранены: зависимости через `workflow_data`, сессии в
`store` с TTL, номер накладной через атомарный `INCR`, вызов модели в
`asyncio.to_thread` с таймаутом, падение провайдера превращается в человеческую
фразу. Добавлено сверх списка: несколько организаций и диалог `/orgs`, кнопка
блокера объясняет, что делать, ответ «да» подтверждает показанное значение.

Полный сценарий (`/orgs` → `/new` → 5 файлов → «готово» → вопросы → карточка →
XML) проходит в `tests/test_bot_flow.py` на заглушках телеграма. **Живьём бот не
запускался: нужен `BOT_TOKEN`.**

Известные дефекты, которые надо устранить:

- `msg.bot["extractor"]` — так в aiogram 3 не работает, нужен проброс
  через `workflow_data` / DI;
- `SESSIONS` в памяти процесса — переносить в Redis с TTL;
- `_resolver()` создаётся на каждый хендлер и мутирует общий `ORG["counter"]` —
  гонка при параллельных сессиях, счётчик вынести в хранилище;
- синхронный `extractor.extract` в async-хендлере блокирует loop;
- нет обработки таймаутов и падений провайдера — бухгалтер не должен видеть трейсбек.

**Приёмка:** полный сценарий проходит локально — `/new` → 5 файлов → «готово» →
вопросы → карточка → XML.

### Задача 5.1. Заявка — ЧАСТИЧНО 10.09.2026

Сделано: заявка на том же движке (`doc_type`), DOCX и текст для мессенджера,

водителя и машину бот просит прислать отдельно после кнопки «Накладная по этой
заявке». Правка условий из самого бота (кнопкой) тоже не сделана — только в
`var/orgs.json`.

Что было в задаче:

- Условия заявки (`DEFAULT_TERMS` в `zayavka.py`) вынести в настройки

- Добавить приём подтверждённой заявки от перевозчика: пришёл скан с подписью

### Задача 6. Справочники — частично

Профили организаций-грузоотправителей уже на диске (`orgs.py`, `var/orgs.json`),
счётчик номеров — в Redis. Справочники контрагентов, ТС и водителей по-прежнему

Postgres вместо памяти: организации по ИНН, ТС по госномеру, водители по ВУ,
последняя накладная по получателю (для «как в прошлый раз»).
ПД водителей в справочнике — минимум необходимого, без сканов.

- Канал определяется ответом поддержки Saby (см. раздел 5), а не догадкой.

## 6. Соглашения по коду

- Python 3.12 по договорённости; локально стоит 3.13.7, ядро на stdlib работает
  на обеих. Стандартная библиотека в ядре. `pydantic` — только на границе
  с моделью, внутрь ядра не тащить.
- Ядро (`fields`, `parse`, `resolve`) не знает ни про Telegram, ни про Saby,
  ни про провайдера модели. Тестируется без сети.
- Комментарии объясняют **почему**, а не что. `# увеличиваем счётчик` — мусор,
  `# пустое умолчание — не догадка, подтверждать нечего` — по делу.
- Тексты для бухгалтера пишутся по-человечески. Не «поле обязательно к
  заполнению», а «без этого накладную не собрать».
- Секреты только в env. Логин Saby даёт доступ ко всему документообороту
  организации — обращаться соответственно.
- В логи не попадают: содержимое документов, ФИО, номера ВУ, паспортные данные.
