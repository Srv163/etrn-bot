# Распознавание документов

Порядок такой: **основной путь — Yandex Vision OCR**, запасной — локальный
tesseract, аварийный — «ничего не распознаём, спрашиваем в диалоге». Бот сам
выбирает лучшее из доступного по настройкам в `.env`.

## Основной путь: Yandex Vision OCR

У сервиса есть готовые модели ровно под наши документы, и они возвращают не
«текст со страницы», а именованные поля:

| Модель | Что читает | Поля |
|---|---|---|
| `passport` | основной разворот паспорта | ФИО, пол, гражданство, дата и место рождения, номер, кем выдан, дата выдачи, код подразделения |
| `driver-license-front` | права, лицевая | ФИО, номер, дата рождения, даты выдачи и окончания |
| `driver-license-back` | права, оборот | номер, стаж, предыдущий номер |
| `vehicle-registration-front` | СТС, лицевая | госномер, VIN, марка, модель, год, шасси, кузов/прицеп, цвет, номер СТС |
| `vehicle-registration-back` | СТС, оборот | собственник, номер СТС |
| `license-plates` | все автономера на фото | точнее общей модели |
| `page`, `handwritten`, `table` | произвольный текст | для заявок и договоров |

Модель выбирается по имени файла: «Вод удост.pdf» → права, «стс …» → СТС,
«Паспорт…» → паспорт, остальное → `page`. Имя файла — самая дешёвая подсказка,
и бухгалтерия называет файлы осмысленно.

**Паспорт нужен для доверенности**, а не для накладной: в Титуле 1 паспортных
реквизитов нет. Поэтому паспортные поля живут в реестре с пометкой
`not_in_xml` (раздел «8а. Водитель — для доверенности»), хранятся в справочнике
водителей и в XML накладной не попадают.

Что настроить:

```bash
ETRN_YANDEX_API_KEY=…      # сервисный аккаунт с ролью ai.vision.user
ETRN_YANDEX_FOLDER_ID=…    # каталог этого аккаунта
```

Технические ограничения сервиса: JPEG, PNG, PDF, до 10 МБ и 20 мегапикселей.
Запрос платный постранично, поэтому на документ делается **ровно один** вызов:
поля и текст приходят в одном ответе.

Всё, что пришло от сервиса, идёт человеку на подтверждение (уверенность 0.8):
цена ошибки в номере прав выше, чем неудобство одного вопроса.

## Запасной путь: локальный tesseract

## Замеры, из которых выбирали

Тестовый файл — `tests/fixtures/zayavka_418.png`: печатная заявка на перевозку
со всеми реквизитами (номер, стороны с ИНН, груз, масса, места, упаковка,
маркировка, машина, водитель, права, времена погрузки).

| Способ | Где | Время | Найдено полей |
|---|---|---|---|
| `qwen2.5vl:3b`, промпт «найди поля и верни JSON» | Hermes, CPU | **653 с** | **0** |
| `qwen2.5vl:3b`, промпт «перепиши текст» | Hermes, CPU | >14 мин, не дождались | — |
| `tesseract -l rus+eng` + разбор по подписям | мак | **0.4 с** | **23** |
| `tesseract -l rus+eng` | Hermes, CPU | 2.7 с | — |

Модель `qwen2.5vl:3b` с Hermes удалена: 3.2 ГБ на диске, где было занято 89%,
за нулевой результат. Вернуть её — одна команда `ollama pull`, ollama на сервере
осталась.

Вывод не «модель плохая», а «инструмент не тот»: маленькая vision-модель на
процессоре не держит ни промпт на 78 полей, ни OCR целой страницы. Печатный
текст читает OCR — это его работа.

## Как это работает теперь

```
скан/фото → OCR (tesseract) → текст → textscan (разбор по подписям)
          → парсеры (ИНН по контрольной сумме, госномер, масса, даты)
          → значения с уверенностью ≤ 0.85 и ссылкой на строку документа
          → человек подтверждает в диалоге
```

Ключевое: реквизиты из документа никогда не принимаются молча. Уверенность
любого распознанного значения не выше 0.85, а источник называет и файл, и строку
(«zayavka_418.png: «Масса брутто: 20 000 кг»»). Ошибка OCR попадёт человеку на
глаза, а не в XML.

Проверка на настоящем файле и на пустом листе:

```bash
PYTHONPATH=. python3 -m etrn_bot.tools.try_vlm tests/fixtures/zayavka_418.png
PYTHONPATH=. python3 -m etrn_bot.tools.try_vlm --blank        # должно быть 0 полей
```

Сквозной прогон на этой заявке: 23 распознанных поля → бот достроил до 68 →
осталось 5 вопросов (код региона погрузки, код тары на подтверждение, состояние
груза, дата заявки без времени, ИНН с несходящейся контрольной суммой — он в
фикстуре вымышленный).

## Настройка

Ничего настраивать не нужно: если `tesseract` с русским языком есть в системе,
бот использует его сам.

```bash
# macOS
brew install tesseract tesseract-lang
# Debian/Ubuntu (на Hermes уже сделано 09.09.2026)
apt install tesseract-ocr tesseract-ocr-rus
```

Переменные (все необязательные):

```bash
ETRN_OCR_LANGS=rus+eng     # именно rus+eng: с одним rus «Volvo FH» читается как «\/о№о ЕН»
ETRN_OCR_TIMEOUT=60
ETRN_OCR_DPI=300           # чем разворачивать PDF; ниже 200 читается плохо
ETRN_OCR_PSM=6             # «единый блок текста» — режим для бланков и карточек
ETRN_VLM_MODE=ocr          # по умолчанию; json — только для сильной модели
```

Что бот умеет открывать: изображения, **PDF** (разворачивается постранично через
`pdftoppm`), **DOCX** и текстовые файлы. Для PDF нужен poppler:
`brew install poppler` на маке, `apt install poppler-utils` на сервере.

Перед распознаванием изображение готовится: обрезаются пустые поля, документ
увеличивается и контрастируется, затем пробуются четыре поворота и берётся тот,
где получилось больше осмысленных слов. Это не украшательство: скан прав лежал
боком в углу листа A4, и без подготовки tesseract выдавал на нём чистый мусор.

## Проверка на настоящих документах (10.09.2026)

Владелец прислал реальную пачку по рейсу: скан водительского удостоверения,
паспорт, три СТС, карточку водителя в Word, файл с ИНН. Сами документы в
репозиторий не попали и удалены с диска сразу после замера — там персональные
данные живого человека. Результат:

| Документ | Время | Найдено полей |
|---|---|---|
| карточка водителя `.docx` | 0.03 с | **5** — ФИО, телефон, марка, госномер, прицеп |
| водительское удостоверение (скан PDF) | 11 с | **1** — номер ВУ |
| СТС, три файла (сканы PDF) | 6–26 с | **0–1** — иногда разрешённая масса |
| паспорт (скан PDF, 5 страниц) | 78 с | **0** — так и задумано |
| печатная заявка (наша фикстура) | 0.4 с | **23** |

Что из этого следует:

1. **Печатное и электронное читается отлично.** Заявка — 23 поля, вордовская
   карточка водителя — 5 полей мгновенно, вообще без OCR. Именно эти документы
   и приходят по каждому рейсу.
2. **Бланки с защитной сеткой OCR не по зубам.** В СТС госномер `АВ1234 99`
   прочитался как `81053577`, марка — как «12-2». Права читаются лучше (номер
   и фамилия), но нестабильно: имя-отчество то распознаётся, то нет.
   Предобработка (обрезка полей, поворот, контраст) помогает, но не спасает.
3. **Паспорт не разбираем сознательно.** В Титуле 1 нет ни одного поля с
   паспортными данными, поэтому доставать их незачем: чем меньше ПД в системе,
   тем лучше. Он прогоняется через OCR и молча даёт ноль полей.
4. **Данные водителя и машины — это справочник, а не распознавание.** Они не
   меняются от рейса к рейсу: занёс один раз (руками или из вордовской карточки)
   — дальше бот тянет их по номеру ВУ и госномеру стратегией LOOKUP. Пытаться
   каждый рейс читать пластиковую карточку прав — решать не ту задачу.

Отдельное ограничение: файл вида `ИНН.txt` с одним числом внутри разбор не берёт —
из текста не видно, чей это ИНН, а угадывать реквизит стороны запрещено
(правило 4 в `CLAUDE.md`). Такие данные заносятся в справочник.

## Когда всё-таки понадобится языковая модель

OCR силён на печатном тексте и слаб там, где текст не печатный:

- фото водительского удостоверения — пластик, мелкий шрифт, блики, угол;
- рукописные правки в накладной;
- мятые и перекошенные сканы, фото «с рук» под наклоном.

**Теперь это измерено, а не предположено** (см. таблицу выше): на сканах ВУ и
СТС OCR даёт от нуля до одного поля. Если такие документы нужно читать
автоматически — нужна облачная модель, и вот тут вопрос ПД встаёт в полный рост:
наружу поедут именно права и паспорта. Альтернатива без всякой отправки —
занести машину и водителя в справочник один раз.

Если OCR на таких файлах окажется плох, включается вариант B: облачная модель.
Клиент готов, нужно вписать три строки в `.env`:

```bash
ETRN_VLM_BASE_URL=https://…/v1
ETRN_VLM_API_KEY=…
ETRN_VLM_MODEL=…
```

Провайдеры с собственной схемой авторизации (GigaChat с OAuth-токеном на 30
минут, Яндекс с IAM-токеном) потребуют адаптера — примерно 40 строк рядом с
`HttpVLMClient`.

**Про персональные данные, фактом:** через облачную модель уйдут фото ВУ и
паспортов. Российский сервис или OCR на своей машине оставляют эти данные внутри
страны; зарубежный — это трансграничная передача ПД со своими требованиями
152-ФЗ. Текущая схема (OCR локально) вопрос закрывает полностью: наружу не
уходит ничего.

## Если бот переедет на Hermes

`tesseract` с русским там уже стоит, ollama осталась без моделей. Помнить:

- диск 54 ГБ, занято 83% — большие модели туда не влезут;
- на сервере работают автобот ST15-v2, форвард ДИОР по cron каждые 15 минут и
  xray на 443. OCR их не трогает (2.7 с на страницу), а вот инференс языковой
  модели занимал 5 ядер из 6 и поднимал load average с 3 до 6.9 — если вернёте
  модель, ставьте ей `CPUQuota` и `Nice`.
