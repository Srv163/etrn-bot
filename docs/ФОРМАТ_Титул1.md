# Титул 1 ЭТрН — что говорит первичка

Выписано 09.09.2026 из **приказа ФНС от 09.12.2021 № ЕД-7-26/1065@, приложение № 1**
(«Формат электронной транспортной накладной», версия формата 5.01, часть 973).
Источник — `../docs/pril1_1065_описание_формата_ЭТрН.docx`, разделы I–II, и сама
схема `../schema/ON_TRNACLGROT_1_973_01_05_01_02.xsd`. Ничего не пересказано по
памяти: каждый пункт ниже прочитан в файле.

## Наш файл — один из восьми

ЭТрН по формату включает **четыре обязательных** файла обмена (грузоотправитель →
приём груза перевозчиком → грузополучатель → выдача груза перевозчиком) и четыре
опциональных (переадресовка, замена водителя/ТС, ПУД перевозчика, ПУД
грузоотправителя). Бот собирает **только первый** — информацию грузоотправителя.
Остальные семь схем лежат в `schema/` для справки, их поля — чужие (`DEFER`).

## Имя файла обмена (задача 2, `filename()`)

```
ON_TRNACLGROT_A_E_O_W_GGGGMMDD_N.xml
```

| Часть | Что это | Откуда берётся |
|---|---|---|
| `ON_TRNACLGROT` | фиксированный префикс титула 1 | константа |
| `A` | идентификатор **перевозчика** — получателя файла, ≤46 символов: первые 3 — код оператора ЭДО перевозчика (присваивает ФНС), остальные ≤43 — GUID участника | **оператор ЭДО**, не бот |
| `E` | идентификатор **грузополучателя** — получателя файла, та же структура | **оператор ЭДО**, не бот |
| `O` | идентификатор **грузоотправителя** — отправителя файла (наш), та же структура | **оператор ЭДО**, не бот |
| `W` | признак доп. получателей: `0` — нет, `1` — есть | политика (у нас `0`) |
| `GGGGMMDD` | дата формирования файла | вычисляется |
| `N` | GUID 36 символов | генерируется |

Расширение — `xml`, строчными или прописными. **Первая строка файла обязана быть**
`<?xml version="1.0" encoding="windows-1251"?>` — кодировка windows-1251, не UTF-8.

> **Следствие, которого не было в постановке.** Три из семи частей имени —
> `A`, `E`, `O` — это идентификаторы участников ЭДО, которые присваивает
> **оператор ЭДО**, а не мы. Бот не может собрать имя файла из документов рейса:
> нужны идентификаторы нашей организации, перевозчика и грузополучателя в системе
> оператора. Пока их нет, единственный рабочий вариант — грузить XML в Saby
> вручную и позволить оператору сформировать имя самому. Это уточняющий вопрос
> к поддержке Saby (блокер 2 в `STATE_ETRN.md`), а не деталь реализации.

Имя файла схемы по приказу — `ON_TRNACLGROT_1_973_01_05_01_xx`, где `xx` — версия
схемы; у нас `xx = 02`.

## Объём схемы

Посчитано инструментом `etrn_bot/tools/xsd_map.py` (разворачивает типы,
внутри `choice` обязательность не наследуется):

- всего узлов (элементы + атрибуты) в Титуле 1 — **974**;
- из них безусловно обязательных — **82**.

Разбивка обязательных по секциям: `СвПогруз` 15, `СвГруз` 10, `СвТС` 9,
`УказГО` 7, `СвГО` 6, `СвГП` 6, `СвВодит` 5, `Подписант` 5, `СвПер` 4,
остальные 15 — атрибуты уровня файла, документа и номера/даты накладной и заказа.

Полные списки: `КАРТА_Титул1_полная.txt` (974 строки) и
`КАРТА_Титул1_обязательные.txt` (82). Пересобрать:

```bash
PYTHONPATH=. python3 -m etrn_bot.tools.xsd_map schema/ON_TRNACLGROT_1_973_01_05_01_02.xsd --required
```

## Что это значит для реестра (задача 1)

В `CLAUDE.md` заявлено 40 полей реестра против 82 обязательных узлов схемы.
Разрыв ожидаем — часть узлов служебные (`@ВерсФорм`, `@КНД`, `@ИдФайл`), часть
собирается из одного поля (ИНН → `СвГО/ИдСв/СвЮЛ/@ИНН` и рядом), — но сверку
делать по узлам схемы, а не по числу полей. Пока `fields.py` не пришёл
(блокер № 0), сверять нечего: половина инструмента для задачи 1 готова
(`xsd_map`), вторая половина — сопоставление с `REGISTRY` — ждёт реестр.

## Чем валидировать (приёмка задач 2 и 3)

`lxml` и `xmlschema` в системе не стоят, но есть системный **`xmllint`**
(libxml 2.09.13, `/usr/bin/xmllint`) — схема Титула 1 им грузится и работает,
проверено 09.09.2026 на заведомо пустом файле:

```bash
xmllint --noout --schema schema/ON_TRNACLGROT_1_973_01_05_01_02.xsd файл.xml
```

Вывод на пустом `<Файл/>` — четыре осмысленные ошибки (`ИдФайл`, `ВерсПрог`,
`ВерсФорм` обязательны, ожидается `ИдПолИной` или `Документ`). Значит приёмку
задачи 2 можно закрывать без установки пакетов; `schema.validate` в `xml_build`
имеет смысл делать обёрткой над `xmllint`, а `lxml` тянуть только если понадобятся
подробные пути ошибок.

Схемы ФНС дополнительно содержат правила Schematron (`sch:`/`usch:` в `appinfo`) —
контроль сумм, взаимозависимость реквизитов, проверка имени файла (`usch:getFileName()`).
`xmllint` их **не проверяет**: XSD-валидация зелёная не означает, что оператор
примет файл. Эти правила отрабатываются либо движком Schematron, либо
фактической загрузкой в Saby.
